# RaiseTimeLine 機能定義書: 認証

Oct 19, 2026 · @tamura

## 1. 概要と権限

メールとパスワードでユーザーを登録・認証し、プロフィールを編集できるようにする機能です。アイコン画像のアップロードは「画像投稿」の機能定義書にあります。

| 対象機能 | 画面 | 説明 |
| --- | --- | --- |
| F-01 ユーザー登録 | S-02 新規登録 | メール・パスワード・表示名・ハンドルで登録し、そのままログイン状態になる |
| F-02 ログイン / ログアウト | S-01 ログイン | メールとパスワードで認証する。ログアウトでは画面側がトークンを破棄する |
| F-03 プロフィール編集 | S-06 プロフィール編集 | 表示名と自己紹介を変更する(アイコンは F-17。詳細は「プロフィール」の機能定義書) |

**権限**

- 登録・ログイン画面は未ログインの人向け。ログイン済みで開いたときは S-03 へ移動する
- プロフィール編集は本人だけ。他人のプロフィールを書き換えるリクエストはサーバー側で拒否する

**認証方式(決定: アクセストークン + リフレッシュトークン)**

ログインと登録の成功時に、2 種類のトークンを発行します。サーバーはセッションを持たない(ステートレス)方式です。

| | アクセストークン | リフレッシュトークン |
| --- | --- | --- |
| 役割 | API を呼ぶための通行証 | アクセストークンを取り直すための、長持ちする鍵 |
| 形式 | JWT(HS256)。中身は iss・sub(ユーザー ID)・iat・exp だけ | 推測できないランダム文字列(32 バイト、base64url) |
| 運び方 | レスポンスボディで返し、画面が `Authorization: Bearer <トークン>` で送る | **HttpOnly Cookie**(`refresh_token`、`Path=/api/auth`、`SameSite=Strict`、`Secure` は環境変数で切替)。ボディには含めない |
| 有効期間 | 既定 15 分(`JWT_EXPIRATION`)。ちょうどで切れる(時計ずれの許容なし) | 既定 7 日(`REFRESH_TOKEN_EXPIRATION`) |
| 画面側の保持 | **メモリのみ**(リロードで消える) | JS から読めない(ブラウザが Cookie として保持) |
| サーバー側 | 保存しない。署名・有効期限・発行者を毎回検証 | DB(`refresh_tokens`)に **SHA-256 ハッシュ**だけ保存 |

- 署名鍵は環境変数 `JWT_SECRET`(32 バイト以上)で渡す。未設定だとサーバーは起動しない
- **ローテーション:** `POST /api/auth/refresh` のたびに新しいリフレッシュトークンを発行し、使った古いものは使用済みにする
- **再利用検知:** 使用済みのトークンが再び提示されたら、盗まれた可能性があるため、その**系統(同じログインから続くトークン全部)を失効**させる。ただし使用済みから 10 秒以内(`REFRESH_REUSE_GRACE`)の再提示は、複数タブの同時更新とみなして 401 を返すだけにし、系統は失効させない
- **ログアウト:** Cookie のリフレッシュトークンの系統を失効させ、Cookie を消す。期限切れでも実行できるよう、アクセストークンは不要。発行済みのアクセストークンは、期限(最長 15 分)まで使える
- **CSRF:** Cookie を使うのは `/api/auth/refresh` と `/api/auth/logout` だけ。`SameSite=Strict` と `Path=/api/auth`、CORS なし(同一オリジン)で防ぐため、CSRF トークンは使わない
- **画面側の動き:** 起動時に `refresh` を呼んでログイン状態を復元する(リロードしても維持)。API が 401 を返したら `refresh` して 1 回だけ再試行し、それも失敗したらログイン画面へ戻す。`refresh` は同時に 1 本にまとめる

## 2. 入力項目と検証

検証は画面(React)とサーバー(Spring Boot)の両方で行います。サーバー側を正とします。

| 項目 | 対象画面 | 必須 | ルール | エラー文言(仮) |
| --- | --- | --- | --- | --- |
| メールアドレス | S-01, S-02 | 必須 | メール形式。255 文字以内。登録時は大文字小文字を區別せず重複不可 | メールアドレスの形式が正しくありません / このメールアドレスは登録済みです |
| パスワード | S-01, S-02 | 必須 | 8〜64 文字。英字と数字をそれぞれ 1 文字以上含む(登録時のみ) | パスワードは 8〜64 文字で、英字と数字を含めてください |
| ユーザーハンドル | S-02 | 必須 | 3〜30 文字。半角英数字と \_ のみ。先頭の @ は入力不要。大文字小文字を區別せず重複不可 | ユーザーハンドルは半角英数字と \_ の 3〜30 文字で入力してください / このハンドルは使われています |
| 表示名 | S-02, S-06 | 必須 | 1〜50 文字。前後の空白は取り除く | 表示名は 1〜50 文字で入力してください |
| 自己紹介 | S-06 | 任意 | 160 文字以内(コードポイント数で数える) | 自己紹介は 160 文字以内で入力してください |

ログインに失敗したときは、「メールアドレスまたはパスワードが正しくありません」とだけ表示します。どちらが違っていたかは示さないです(メールの登録有無を探されないため)。

## 3. 処理の流れ

**ユーザー登録(F-01)**

1. 画面で入力を検証し、POST /api/auth/signup を呼ぶ
2. サーバーで再度検証する。形式のエラーは 400
3. メールとハンドルの重複を確認する。重複していれば 409
4. パスワードを BCrypt でハッシュ化し、users に保存する
5. そのままログイン状態にして(アクセストークンを発行し、リフレッシュトークンを Cookie で返す)、201 を返す
6. 画面はアクセストークンをメモリに保持し、S-03 へ移動する

**ログイン(F-02)**

1. 画面でメールとパスワードを送る(POST /api/auth/login)
2. メールで users を探し、BCrypt で照合する
3. 一致しなければ 401(メールとパスワードのどちらが違うかは示さない)
4. 一致すればアクセストークンを発行し、リフレッシュトークンを Cookie で返して 200(ログインのたびに新しい系統になる。別の端末のログインには影響しない)
5. 画面はアクセストークンをメモリに保持し、ログイン前に開こうとした画面があればそこへ、なければ S-03 へ移動する

**ログイン状態の復元と更新(F-02)**

1. 画面の起動時(リロード含む)と、API が 401 を返したときに、POST /api/auth/refresh を呼ぶ(Cookie が自動で送られる)
2. サーバーはリフレッシュトークンを検証し、使用済みにして、新しいアクセストークンと新しいリフレッシュトークン(Cookie)を返す(200)
3. 無効・期限切れ・失効済み・使用済みなら 401(`INVALID_REFRESH_TOKEN`)で Cookie を消す。画面は未ログインとして S-01 へ移動する

**ログアウト(F-02)**

1. POST /api/auth/logout を呼ぶ(アクセストークンは付けない)
2. サーバーはリフレッシュトークンの系統を失効させ、Cookie を消して 204 を返す
3. 画面は保持しているアクセストークンを破棄し、S-01 へ移動する。通信に失敗しても、この端末ではログアウトする

**プロフィール編集(F-03)**

画面・処理の流れ・API の詳細は「プロフィール」の機能定義書にあります。認証に関わるのは次の 2 点です。

1. S-06 を開くと GET /api/auth/me で現在の値を取得し、フォームに入れる
2. 保存で PUT /api/users/me を呼ぶ。対象はログイン中の本人の行だけ

## 4. API

パスは仮です。エラーはすべて { "code": "...", "message": "..." } の形式で返します。入力検証エラー(400)には、項目ごとのメッセージを入れた `fieldErrors`(項目名 → メッセージ)も付けます。実装済みの code は `VALIDATION_ERROR`(400)・`LOGIN_FAILED`(401)・`UNAUTHORIZED`(401)・`INVALID_REFRESH_TOKEN`(401)・`FORBIDDEN`(403)・`EMAIL_ALREADY_EXISTS` / `HANDLE_ALREADY_EXISTS`(409)です。

| メソッド | パス | 認証 | リクエスト | 成功 | 失敗 |
| --- | --- | --- | --- | --- | --- |
| POST | /api/auth/signup | 不要 | email, password, handle, displayName | 201 + トークンとユーザー(下記)、Set-Cookie(リフレッシュトークン) | 400 検証エラー / 409 メールまたはハンドルが重複 |
| POST | /api/auth/login | 不要 | email, password | 200 + トークンとユーザー(下記)、Set-Cookie | 400 検証エラー / 401 認証失敗 |
| POST | /api/auth/refresh | Cookie | なし(Cookie のリフレッシュトークン) | 200 + トークンとユーザー(下記)、新しい Set-Cookie | 401 リフレッシュトークンが無効(Cookie も削除) |
| POST | /api/auth/logout | 不要(Cookie があれば失効) | なし | 204、Cookie 削除 | なし(常に 204) |
| GET | /api/auth/me | 必要 | なし | 200 + ログイン中のユーザー(bio, avatarKey を含む) | 401 未ログイン |
| PUT | /api/users/me | 必要 | displayName, bio, avatarKey(任意。省略は変更なし、null は削除) | 200 + 更新後のユーザー(詳細は「プロフィール」) | 400 検証エラー / 401 未ログイン |

登録・ログイン・リフレッシュの成功レスポンスは次の形です。`user` は `GET /api/auth/me` と同じ内容(id, handle, displayName。bio, avatarKey は設定されていれば含む)です。

```json
{ "accessToken": "eyJ...", "tokenType": "Bearer", "expiresIn": 900, "user": { "id": 1, "handle": "tamura", "displayName": "田村" } }
```

「必要」と書いた API は、`Authorization: Bearer` ヘッダーがないか、トークンが不正(署名の改ざん・期限切れ・発行者違い)なら 401 を返します。

## 5. DB とセキュリティ

使うテーブルは users と refresh_tokens です(users の列は要件定義書の「7. データモデル」を参照)。メールとハンドルの重複を、大文字小文字を區別しない一意インデックスで DB に保証します。

```sql
CREATE UNIQUE INDEX uq_users_email_lower  ON users (lower(email));
CREATE UNIQUE INDEX uq_users_handle_lower ON users (lower(handle));
```

**refresh_tokens**(リフレッシュトークンの管理。トークン本体は保存しない)

| 列 | 型 | 制約 | 内容 |
| --- | --- | --- | --- |
| id | BIGINT | PK、自動採番 | |
| user_id | BIGINT | NOT NULL、FK → users(ON DELETE CASCADE) | 持ち主。ユーザーを消すとトークンも消える |
| family_id | VARCHAR(36) | NOT NULL、索引 | ログイン 1 回ごとの系統。ローテーションで発行されるトークンは同じ値を引き継ぐ |
| token_hash | VARCHAR(64) | NOT NULL、UNIQUE | トークンの SHA-256(16 進 64 桁) |
| expires_at | TIMESTAMPTZ | NOT NULL | 有効期限 |
| used_at | TIMESTAMPTZ | NULL | ローテーションで使用済みにした時刻 |
| revoked_at | TIMESTAMPTZ | NULL | 失効(ログアウト・再利用検知)した時刻 |
| created_at | TIMESTAMPTZ | NOT NULL | 作成時刻 |

ローテーションは、`UPDATE … SET used_at=now() WHERE token_hash=? AND used_at IS NULL AND revoked_at IS NULL AND expires_at>now()` の更新件数で成否を決めます。同じトークンで同時に更新が来ても、成功するのは 1 件だけです。

- パスワードは BCrypt(Spring Security の BCryptPasswordEncoder)でハッシュ化し、平文は保存もログ出力もしない
- API のレスポンスに password\_hash を含めない(専用の返却用 DTO を使う)
- アクセストークンは署名(HS256)と有効期限と発行者を毎回検証する。署名鍵はコードに書かず、環境変数で渡す
- リフレッシュトークンは HttpOnly(JS から読めない)・SameSite=Strict・Path=/api/auth の Cookie で運び、DB にはハッシュだけを保存する(DB が漏れてもトークンは使えない)
- 本番(HTTPS)では Cookie の Secure を必ず有効にする(`REFRESH_COOKIE_SECURE=true`)
- 通信は HTTPS(ALB で終端)。HTTP で来たときは HTTPS へリダイレクトする

## 6. エラーと境界値

- 同じメール・ハンドルで同時に登録されたとき: DB の一意制約違反を捕まえて 409 に変換する(事前チェックだけに頑りない)
- アクセストークンの期限が切れた状態で API を呼んだとき: 401 を返し、画面は `refresh` して 1 回だけ再試行する。それも失敗したら、トークンを破棄して S-01 へ移動し、ログイン後に元の画面へ戻す
- 複数のリクエストが同時に 401 になったとき: 画面は `refresh` を 1 回にまとめる(2 回目が使用済みトークンになって誤って失効しないため)
- 複数タブで同時に `refresh` したとき: 先に届いた 1 件だけが成功し、もう一方は 401(猶予内なので系統は失効しない)。Cookie は共有なので、後から再試行すれば成功する
- リフレッシュトークンが盗まれて使用済みのものが再提示されたとき: 猶予を過ぎていれば系統ごと失効し、正規の利用者も再ログインになる
- アクセストークンは有効だがユーザーが削除済みのとき: 401 を返す
- 通信に失敗したとき(オフライン等): 画面はログアウト扱いにせず、「通信に失敗しました。しばらくしてからやり直してください」(仮)と表示する
- パスワードの長さ: 64 文字を超える入力は拒否する(BCrypt の入力上限 72 バイトを超えないようにする)
- 自己紹介 160 文字ちょうどは可、161 文字目はエラー。絵文字は 1 文字と数える
- 連続で送信ボタンを押したとき: 送信中はボタンを無効化する

## 7. 受け入れ条件

- [ ] 正しい入力で登録すると、ログイン状態で S-03 が開く
- [ ] 同じメール(大文字小文字違いを含む)での再登録はエラーになる
- [ ] 同じハンドル(大文字小文字違いを含む)での再登録はエラーになる
- [ ] 間違ったパスワードではログインできず、メールとパスワードのどちが違うかがわからない文言になる
- [ ] DB に平文のパスワードが残らない
- [ ] ログアウト後に「戻る」を押しても、ログインが必要な画面の内容が見えない(トークンを破棄済みで API が 401 になる)
- [ ] ブラウザをリロードしても、ログイン状態が維持される(リフレッシュで復元)
- [ ] アクセストークンの期限が切れても、画面の操作が自動で続行される
- [ ] 使用済みのリフレッシュトークンを再提示すると 401 になり、系統の最新のトークンも使えなくなる
- [ ] リフレッシュトークンは JS(`document.cookie`・Web ストレージ)から見えず、DB には平文で残らない
- [ ] 他人のプロフィールを PUT /api/users/me で変更できない
- [ ] 自己紹介 161 文字は画面とサーバーの両方で拒否される
