# RaiseTimeLine ログ設計と閾値

Nov 3, 2026 · @tamura

## 1. 概要

バックエンドは、ログを **1 行 1 JSON** で標準出力に出します(構造化ログ)。全環境で同じ形式です。ログを集める仕組みは、まだ決めていません。

- 実装: `logstash-logback-encoder` と `backend/src/main/resources/logback-spring.xml`
- リクエスト単位のログ: `RequestLoggingFilter`(完了時に 1 リクエスト 1 行)
- 閾値の定数: `LogThresholds`(値を変えるときは、このドキュメントも直す)
- アラートは設計しません。閾値は「遅い」とログに目印を付けるためのものです

### Datadog などへの連携

今は Datadog を使いません。使うことになったら、アプリのコードを変えずに、次の設定だけで連携できる形にしてあります。

| 連携に必要なもの | 今の状態 |
| --- | --- |
| 標準出力の JSON を読む | 対応済み(Datadog Agent は、コンテナの標準出力の JSON をそのまま解析する) |
| `service` / `env` / `version` のタグ | 全行に付いている。環境変数 `LOG_SERVICE` / `LOG_ENV` / `LOG_VERSION` で変える |
| ログレベル・時刻・メッセージ | `level` / `timestamp` / `message` として出ている(Datadog の標準の読み替えに合う) |
| ログとトレースの紐づけ | Datadog の Java トレーサー(`-javaagent`)を付けると、`dd.trace_id` / `dd.span_id` が自動で全行に入る |

アプリ側で、相関 ID は `requestId` として持ちます。トレーサーを付けなくても、1 リクエストのログをたどれます。

## 2. ログのフィールド

### 2.1 すべての行に付くもの

| フィールド | 内容 |
| --- | --- |
| `timestamp` | 時刻(ISO 8601、タイムゾーン付き) |
| `level` | INFO / WARN / ERROR |
| `message` | 人が読む文 |
| `logger_name` / `thread_name` | 出力元 |
| `service` / `env` / `version` | アプリ名・環境・バージョン |
| `requestId` | リクエストの相関 ID。ヘッダー `X-Request-Id` があれば引き継ぎ、無ければ UUID を作る。レスポンスのヘッダーにも返す |
| `userId` | ログイン済みのときだけ。ユーザー ID(JWT の `sub`) |
| `stack_trace` | 例外があるとき |

`X-Request-Id` は、英数字・`.`・`_`・`-` の 64 文字までだけ引き継ぎます。それ以外は捨てて、新しく作ります。

### 2.2 アクセスログ(`logger_name` = `http.access`)

| フィールド | 内容 |
| --- | --- |
| `method` / `path` | HTTP メソッドとパス。クエリ文字列は含めない |
| `status` | レスポンスのステータス |
| `durationMs` | 処理時間(ミリ秒) |
| `slow` | 3 章の閾値を超えたら true |

API 仕様と Swagger UI(`/api/v3/api-docs`、`/api/swagger-ui`)は記録しません。

### 2.3 その他のログ

| 出す場面 | レベル | 主なフィールド |
| --- | --- | --- |
| 業務エラー(`ApiException`。入力の誤り、権限なし、重複など) | WARN | `errorCode`、`status` |
| 想定外の例外(500) | ERROR | `errorType`、`stack_trace` |
| S3 の署名付き URL の発行・削除の失敗 | WARN | `operation`、`imageKey`、`stack_trace` |
| S3 の呼び出しが閾値より遅い | WARN | `operation`、`imageKey`、`durationMs`、`thresholdMs` |

## 3. ログレベルの使い分け

| レベル | 使う場面 |
| --- | --- |
| ERROR | アプリのバグや障害で、利用者が正しく使えなかった。5xx のアクセスログ、想定外の例外 |
| WARN | 利用者の操作や外部要因で失敗した、または遅かった。4xx のアクセスログ、業務エラー、閾値を超えた処理、S3 の失敗 |
| INFO | 正常に終わったリクエストと、起動・停止 |
| DEBUG 以下 | 出さない。必要になったら、環境変数 `LOGGING_LEVEL_COM_RAISETIMELINE=DEBUG` などで一時的に上げる |

同じ 1 件のエラーで、アクセスログ(WARN / ERROR)と原因のログ(業務エラー・想定外の例外)の 2 行が出ます。`requestId` で結びつけられます。

## 4. 閾値

超えると、アクセスログが WARN になり `slow` が true になります。値は初期の目安で、実際の処理時間を見て見直します。

### 4.1 リクエスト全体

| 種類 | 対象 | 閾値 | 根拠 |
| --- | --- | --- | --- |
| 認証 | `/api/auth/` 配下 | 1000 ms | BCrypt のハッシュ計算(数百 ms)を含むため、他より長くとる |
| 一覧 | GET の `/api/timeline`(新着を含む)、`/api/search`、`/api/users`(ユーザー投稿・フォロー一覧を含む)、コメント一覧 | 500 ms | DB から 1 ページ(既定 20 件)を引く。カーソル方式で、ページが深くなっても遅くならない設計 |
| 画像 | `/api/images/` 配下 | 800 ms | S3 の署名付き URL の発行。画像本体はアプリを通らない |
| その他 | 投稿・コメント・いいね・フォロー・プロフィール更新など | 300 ms | 主キーや一意制約を使う 1〜数回の SQL で終わる |

### 4.2 外部呼び出し(S3)

| 処理 | 閾値 | 根拠 |
| --- | --- | --- |
| 表示用の署名付き URL の発行 | 100 ms | SDK 内の署名計算だけで、ネットワークを使わない。同じ URL は有効期間の半分まで使い回す |
| 画像の削除 | 1000 ms | S3 へのネットワーク通信。失敗しても利用者には成功を返す |

### 4.3 閾値としては持たないもの

| 項目 | 理由 |
| --- | --- |
| DB の個別の SQL の時間 | アクセスログの `durationMs` で足りる。SQL ごとの計測が必要になったら、MyBatis のログで別に考える |
| 新着件数の上限 | 閾値ではなく仕様(最大 50 件) |

## 5. ログに出してはいけない情報

- パスワード、アクセストークン、リフレッシュトークン、Cookie、`Authorization` ヘッダー
- クエリ文字列(カーソルなどが入る)、リクエストとレスポンスの本文
- 投稿・コメントの本文、メールアドレス

ユーザーは `userId`(数値)だけで特定します。S3 のキー(`imageKey`)は、推測できない UUID を含むため記録します(画像を消せなかったときに、後で手で消すために必要)。
