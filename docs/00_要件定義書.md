# RaiseTimeLine 要件定義書

Oct 19, 2026 · @tamura

## 1. 目的

RaiseTimeLine は、テキスト中心のタイムラインに「数字の競争」を持ち込まない、学習用の SNS 風アプリです。複数ユーザーが使う前提で設計し、投稿・コメント・いいね・フォローを第三者同士でやり取りできるようにします。

- ログイン、投稿、コメント、いいね、画像アップロードという、SNSの基本機能をひと通り実装して学ぶ
- 複数ユーザー前提のデータ設計(ユーザーと投稿・コメント・いいねの多対多の関係)を身につける

**差別化ポイント**

| 項目 | X / Twitter | RaiseTimeLine |
| --- | --- | --- |
| インプレッション数の表示 | あり | **なし** |
| リツイート(リポスト) | あり | **なし** |
| いいね数・コメント数の表示 | あり | あり |

## 2. 想定ユーザー・利用シーン

- 受講生・個人の利用者。複数人が同時に使うことを想定する
- 自分以外のユーザーの投稿にも、いいね・コメントができる
- 気になるユーザーを検索してフォローし、「フォロー中」タブで投稿を追いかける
- 数字(インプレッション)を気にせず、文章や画像を気軽に投稿する

## 3. スコープ

今回のバージョン(v0.3)で「作るもの」と「作らないもの」を分けます。

| 対象(今回作る) | 対象外(今回は作らない) |
| --- | --- |
| ユーザー登録・ログイン・ログアウト、プロフィール編集 | リツイート / 引用 |
| タイムライン(「フォロー中」「全体」の2タブ)、投稿の作成・編集・削除 | インプレッション数の計測・表示 |
| コメント(投稿への返信) | DM、通知、ハッシュタグ |
| いいね(付与・取消、件数表示) | 投稿の全文検索(検索対象はユーザーのみ) |
| 画像付き投稿(S3 に保存) | 動画投稿、管理者機能 |
| 一方向のフォロー、フォロー数・フォロワー数の表示 | 相互フォローの承認制、ブロック・ミュート |
| ユーザー検索(@ハンドル・表示名の部分一致) |  |

## 4. 機能要件

機能は 7 機能群・23 機能です。機能ごとの ID、概要、優先度、状態は [RaiseTimeLine 機能一覧](./01_機能一覧.md) にまとめ、詳細な仕様(画面・入力検証・API・DB・受け入れ条件)は機能群ごとの機能定義書に書きます(プロフィールの F-03・F-08・F-17 だけは、機能群をまたいで [機能定義書: プロフィール](./17_機能定義書_プロフィール.md) にまとめます)。ここでは群ごとの要点だけを示します。

| 機能群 | 機能 ID | 要点 |
| --- | --- | --- |
| 認証 | F-01 〜 F-03 | メールとパスワードで登録・ログイン。ユーザーハンドル(@id)を持ち、プロフィール(表示名・自己紹介・アイコン。ハンドルとメールは変更不可)を本人だけが編集できる。詳細は機能定義書: プロフィール |
| タイムライン・投稿 | F-04 〜 F-08, F-23 | 「フォロー中」「全体」の2タブ。本文は 280 文字まで。自分の投稿は本文を編集・削除でき、編集した投稿には「編集済み」を表示。いいね数とコメント数を表示 |
| コメント | F-09 〜 F-12 | 第三者を含む全ユーザーが投稿にコメントできる(280 文字まで)。コメント数を表示 |
| いいね | F-13, F-14 | 1人1投稿につき1回。付与・取消のトグル。いいね数と「自分がいいね済みか」を表示 |
| 画像投稿 | F-15 〜 F-17 | 1投稿に最大4枚、各5MB。S3 に保存し、DB には S3 キーを持つ |
| フォロー | F-18 〜 F-20 | 一方向。フォロー・解除、フォロー数・フォロワー数、一覧表示 |
| ユーザー検索 | F-21, F-22 | @ハンドル・表示名の部分一致。結果からその場でフォローできる |

## 5. 非機能要件

学習用の規模を前提に、セキュリティとデータの整合性を優先します。数値はすべて仮です。技術スタックとインフラは第 8 章にあります。

| 観点 | 要件 |
| --- | --- |
| セキュリティ | パスワードは BCrypt でハッシュ化して保存する(Spring Security)。通信は HTTPS。SQL はプレースホルダーで組み立てる。React の標準エスケープを使い、HTML をそのまま挿入する処理は使わない(XSS 対策)。認証は、短命な JWT のアクセストークン(Bearer ヘッダー、メモリ保持)と、HttpOnly・SameSite=Strict の Cookie で運ぶリフレッシュトークン(DB にはハッシュのみ保存、ローテーションと再利用検知あり)の組み合わせ |
| 権限チェック | 削除は、サーバー側で「自分の投稿・コメントか」を必ず確認する(画面でボタンを隠すだけにしない) |
| 入力検証 | 投稿・コメントは 280 文字まで。文字数はコードポイント数で数え、画面とサーバーの両方で検証する |
| データの整合性 | いいねとフォローの二重付与を DB の複合主キーで防ぐ。自分自身のフォローは CHECK 制約で防ぐ。投稿削除でコメント・いいね・画像も連動削除 |
| 画像 | 拡張子だけでなく中身(MIME タイプ)も検証する。上限は1枚5MB、4枚まで。S3 のバケットは非公開とし、ブラウザは署名付き URL でアップロード・取得する。ファイル名はランダムなキーに置き換える |
| 性能 | 一覧はどれも 1 回 20 件。created\_at にインデックスを張り、N+1 問題を避けて件数は1つのクエリでまとめて取る。ユーザー検索は pg\_trgm のインデックスで部分一致を速くする |
| ユーザービリティ | スマートフォン幅でも崩れない(レスポンシブ)。送信中はボタンを無効化し、二重送信を防ぐ |
| プライバシー | インプレッションなどの閲覧ログを、ユーザー向けにも内部集計としても持たない(差別化ポイント) |

**画面一覧**

| ID | 画面 | URL(仮) | ログイン | 主な構成要素 | 関連機能 |
| --- | --- | --- | --- | --- | --- |
| S-01 | ログイン | /login | 不要 | メール、パスワード、ログインボタン、新規登録へのリンク | F-02 |
| S-02 | 新規登録 | /signup | 不要 | メール、パスワード、表示名、ユーザーハンドル、登録ボタン | F-01 |
| S-03 | タイムライン(ホーム) | / | 必要(仮) | タブ(フォロー中 / 全体)、投稿フォーム(本文 280 文字、画像添付、投稿ボタン)、投稿カード一覧(末尾までスクロールすると続きを自動で読み込む)、新着バー(「N件の新しい投稿を表示」) | F-04 〜 F-07, F-11, F-13 〜 F-16 |

**画面遷移**

&#91;embedded content: 画面遷移図 · 8画面\]

未ログインで制限された画面を開くと、どこからでも S-01 へ遷移します。ログインや登録が終わると S-03 へ進み、各画面のヘッダーのロゴで S-03 に戻れます。

**投稿カード(タイムライン・詳細・プロフィールで共通)**

いいね数とコメント数はカードの下部に並べます。インプレッション数とリツイートボタンは置きません。

```text
+--------------------------------------------------+
| (アイコン)  表示名  @handle  ・ 3分前       [削除]*  |
|                                                  |
| 本文テキスト………………………………………………………       |
|                                                  |
| +--------------+  +--------------+               |
| |   画像 1    |  |   画像 2    |   (最大4枚)     |
| +--------------+  +--------------+               |
|                                                  |
|  💬 12 (コメント数)      ♡ 34 (いいね数)         |
+--------------------------------------------------+
  * 自分の投稿だけに表示。いいね済みのときは♡を塗りつぶしで示す
```

**画面ごとの振る舞い**

- タイムライン: 既定は「フォロー中」タブ(自分の投稿も含む)。フォロー中が 0 人のときは「ユーザーを探してフォローしよう」と案内し、「全体」タブへの切替も出す
- カード: カード本体をクリックで投稿詳細へ。アイコン・表示名をクリックでプロフィールへ。♡ はその場でトグルし、画面遷移しない。自分の投稿には「編集」「削除」を出す。編集を押すと本文を入力欄に切り替えて保存でき、保存後は「編集済み」を表示する(画像は変更できない)
- 投稿詳細: 💬 を押すとコメント入力欄にフォーカス。コメント送信後は、一覧の末尾に追加し、コメント数を +1 する
- プロフィール: 他人のプロフィールではフォロー / フォロー中をトグル。押した直後にフォロワー数を +1 / − 1 する。自分のプロフィールにはフォローボタンを出さない
- ユーザー検索: 入力を止めて 300ms 後、または Enter で検索する。空文字では検索しない。0 件のときは「見つかりませんでした」と表示する。結果の行からその場でフォローできる
- 未ログインで投稿・コメント・いいね・フォローを押したとき: ログイン画面へ遷移し、ログイン後に元の画面へ戻る
- エラー表示: 280 文字の超過、画像の容量・形式違反は、入力欄の下に赤字で表示する

## 7. データモデル

6つのテーブルで構成します(ER図の対象)。ユーザーと投稿を「いいね」と「コメント」が、ユーザー同士を「フォロー」が結びます。ほかに、認証用の refresh\_tokens テーブル(ログイン状態の更新用トークンのハッシュを保存する。列は機能定義書: 認証の「5. DB とセキュリティ」)を持ちます。DB は PostgreSQL(RDS)で、下記の型は仮です(DATETIME は PostgreSQL では TIMESTAMPTZ に読み替えます)。インプレッション用・リツイート用のテーブルは作りません。

**ER図**

| user\_id | BIGINT | FK → users.id, NOT NULL | コメントした人(第三者を含む) |

| カラム | 型(仮) | 制約 | 説明 |
| --- | --- | --- | --- |
| user\_id | BIGINT | PK(複合), FK → users.id | いいねした人(第三者を含む) |
| post\_id | BIGINT | PK(複合), FK → posts.id | いいねされた投稿。投稿削除で連動削除 |
| created\_at | DATETIME | NOT NULL | いいね日時 |

複合主キー (user\_id, post\_id) により、同じユーザーが同じ投稿に二度いいねできないことを DB の制約として保証します。

follows(フォロー)

| カラム | 型(仮) | 制約 | 説明 |
| --- | --- | --- | --- |
| follower\_id | BIGINT | PK(複合), FK → users.id | フォローする人 |
| followee\_id | BIGINT | PK(複合), FK → users.id, INDEX | フォローされる人。フォロワー一覧と件数の取得に使う |
| created\_at | DATETIME | NOT NULL | フォロー日時 |

複合主キーで二重フォローを防ぎ、CHECK (follower\_id <> followee\_id) で自分自身のフォローを防ぎます。ユーザーが削除されたときは、関係する行も連動削除します。

**リレーション**

| 親 | 子 | 関係 | 意味 |
| --- | --- | --- | --- |
| users | posts | 1 : N | 1人が複数の投稿をする |
| users | comments | 1 : N | 1人が複数のコメントをする |
| users | likes | 1 : N | 1人が複数の投稿にいいねする |
| users | follows(follower\_id) | 1 : N | 1人が複数のユーザーをフォローする |
| users | follows(followee\_id) | 1 : N | 1人が複数のユーザーにフォローされる |
| posts | comments | 1 : N | 1つの投稿に複数のコメントが付く |
| posts | likes | 1 : N | 1つの投稿に複数のいいねが付く |
| posts | post\_images | 1 : N | 1つの投稿に最大4枚の画像が付く |
| users ↔ posts | likes を介して | N : N | いいねはユーザーと投稿の多対多を表す |
| users ↔ users | follows を介して | N : N | フォローはユーザー同士の多対多(一方向)を表す |

**件数の求め方**

いいね数とコメント数は列として持たず、表示のたびに COUNT で数えます。データの食い違いが起きないことを優先した学習向けの選択です。遅くなったら、posts に like\_count / comment\_count 列を足す案を検討します。

```sql
SELECT p.id, p.body, p.created_at, u.display_name, u.handle,
       (SELECT COUNT(*) FROM likes    l WHERE l.post_id = p.id) AS like_count,
       (SELECT COUNT(*) FROM comments c WHERE c.post_id = p.id) AS comment_count,
       EXISTS (SELECT 1 FROM likes l
               WHERE l.post_id = p.id AND l.user_id = :me)      AS liked_by_me
FROM posts p
JOIN users u ON u.id = p.user_id
ORDER BY p.created_at DESC
LIMIT 20;
```

**「フォロー中」タブの取得**

自分とフォロー先の投稿だけに絞ります。「全体」タブはこの WHERE を外すだけです。

```sql
WHERE p.user_id = :me
   OR p.user_id IN (SELECT followee_id FROM follows WHERE follower_id = :me)
```

**ユーザー検索のクエリ**

@ハンドルと表示名の部分一致で探し、前方一致を上位に並べます。部分一致(%検索語%)は通常のインデックスが効かないため、PostgreSQL の pg\_trgm で GIN インデックスを張ります。入力の %・\_・\\ はエスケープしてから渡します。

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_users_handle_trgm       ON users USING gin (handle       gin_trgm_ops);
CREATE INDEX idx_users_display_name_trgm ON users USING gin (display_name gin_trgm_ops);

SELECT u.id, u.handle, u.display_name, u.avatar_key,
       EXISTS (SELECT 1 FROM follows f
               WHERE f.follower_id = :me AND f.followee_id = u.id) AS followed_by_me
FROM users u
WHERE u.handle       ILIKE '%' || :q || '%' ESCAPE '\'
   OR u.display_name ILIKE '%' || :q || '%' ESCAPE '\'
ORDER BY (u.handle ILIKE :q || '%' ESCAPE '\'
       OR u.display_name ILIKE :q || '%' ESCAPE '\') DESC,
         u.handle
LIMIT 20 OFFSET :offset;
```

## 8. 制約・前提条件

**技術スタック**

| 領域 | 採用 | 備考 |
| --- | --- | --- |
| フロントエンド | React 19 + TypeScript 6 + Vite 8 | TypeScript の採用は決定(7.0 のネイティブプレビューは typescript-eslint が未対応のため避ける)。ルーティングは react-router、テストは Vitest + Testing Library。開発時は Vite のプロキシで `/api` を同一オリジン化する |
| バックエンド | Spring Boot 4.0.8(Java 25、Gradle) | REST API。認証は Spring Security。DB アクセスは MyBatis、スキーマ管理は Flyway(MyBatis スターターに対応する最新の Spring Boot を採用) |
| データベース | PostgreSQL(AWS RDS) | ユーザー検索に pg\_trgm を使う |
| 画像ストレージ | AWS S3(利用確定) | 署名付き URL でアップロード・取得。DB には S3 キーを保存 |
| 実行環境 | AWS EC2 + ALB | 構築するかは未決。前提とする構成は [RaiseTimeLine インフラ構成図](./20_インフラ構成図.md) にある |

**インフラ(現時点の前提)**

AWS でサーバーを構築するかは未決です。構築する場合は、ALB の背後に EC2 を置き、EC2 から RDS(PostgreSQL)と S3 を使う構成を前提に設計します。

**制約**

- サーバーは 1 台構成を前提とする。認証はステートレスな JWT のため、複数台にしても認証の持ち方は変わらない(署名鍵を全台で共有する)
- 画像の S3 バケットは非公開とする
- インプレッション数の計測・表示とリツイートは作らない
- 技術スタックとインフラは、この文書の更新で変えられる。機能ごとの詳細は機能定義書(機能一覧から辞れる)を参照
