# RaiseTimeLine 機能定義書: タイムライン・投稿

Oct 20, 2026 · @tamura

## 1. 概要と権限

投稿を作成・編集・削除し、タイムラインとプロフィールで一覧表示する機能です。数字はいいね数とコメント数だけを出し、インプレッション数とリツイートは扱いません。

| 対象機能 | 画面 | 説明 |
| --- | --- | --- |
| F-04 タイムライン表示 | S-03 | 「フォロー中」「全体」の2タブで、投稿を新しい順に表示する。他のユーザーの新着投稿を定期的に確認し、「N件の新しい投稿を表示」バーで知らせる |
| F-05 投稿作成 | S-03 | 本文(280 文字まで)と画像で投稿する(画像は未実装。現在は本文のみ) |
| F-06 投稿削除 | S-03, S-04, S-05 | 自分の投稿だけ削除できる |
| F-07 続きの読み込み | S-03, S-05 | 20 件ずつ、末尾までスクロールすると自動で読み込む(無限スクロール) |
| F-08 ユーザープロフィールページ | S-05 | プロフィールと、その人の投稿一覧を見る(プロフィールの仕様は「プロフィール」の機能定義書) |
| F-23 投稿編集 | S-03, S-04, S-05 | 自分の投稿の本文だけ編集できる。画像は変更できない。編集した投稿には「編集済み」を表示する |

**タブの動き**

| タブ | 表示する投稿 | 既定 |
| --- | --- | --- |
| フォロー中 | 自分と、フォローしているユーザーの投稿(フォローしていなければ自分の投稿のみ) | ✓ |
| 全体 | すべてのユーザーの投稿 |  |

フォロー中が 0 人で、自分の投稿も無いときは、「まだ投稿がありません。投稿するか、気になるユーザーをフォローしましょう。」と案内し、「全体」タブへ切り替えるボタンを出します(ユーザー検索 S-07 の実装後は、検索への案内も加えます)。選んだタブはブラウザに覚えさせることもできますが、今回は毎回「フォロー中」から始めます。表示中のタブをもう一度押すと、そのタブを最新の状態に更新して先頭へ戻ります。

**権限**

| 操作 | 未ログイン | ログイン済み(本人) | ログイン済み(第三者) |
| --- | --- | --- | --- |
| タイムライン・プロフィールの閲覧 | 不可(現在の実装。S-03 はログイン必須) | 可 | 可 |
| 「フォロー中」タブ | 不可 | 可 | — |
| 投稿する | 不可 | 可 | — |
| 投稿を削除する | 不可 | 可 | 不可 |
| 投稿を編集する | 不可 | 可 | 不可 |

## 2. 入力項目と処理の流れ

| 項目 | 必須 | ルール | エラー文言(仮) |
| --- | --- | --- | --- |
| 本文 | 必須(画像機能の実装後は、画像が無いときだけ必須) | 280 文字以内(コードポイント数)。前後の空白を取り除く。空白や改行だけは不可。途中の改行は保持する | 本文を入力してください(画像実装後は「本文または画像を入れてください」)/ 280 文字以内で入力してください |
| 画像 | 任意 | 最大 4 枚。詳細は「画像投稿」の機能定義書を参照 | 画像は 4 枚までです |

画面には「残り文字数」を表示し、280 文字を超えると(または本文が空のとき)投稿ボタンを無効にします。

**タイムライン表示(F-04, F-07)**

1. S-03 を開くと、tab=following で先頭 20 件を取得する
2. タブを切り替えると、tab=all で取り直す(カーソルはリセット)
3. 一覧の末尾が画面に近づくと(末尾の 300px 手前)、直前のレスポンスの nextCursor を渡して続きを 20 件取得し、末尾に足す(無限スクロール。「もっと見る」ボタンは置かない)
4. nextCursor が null になったら、それ以上は読み込まない。続きの取得に失敗したときは、末尾に「読み込みに失敗しました。再試行」を出す
5. 一覧の取得に失敗したときは、エラーと「再読み込み」ボタンを出す

**新着の確認(F-04)**

1. 一覧を表示している間、30 秒ごとに GET /api/timeline/new で、基準の投稿 ID(sinceId。サーバーから受け取った一覧の先頭の投稿の ID で、自分の投稿では進めない。手順 5 を参照)より新しい投稿を確認する。画面が隠れている間は確認せず、見える状態に戻った時点ですぐ確認する
2. 新着があれば、一覧の上部に「N件の新しい投稿を表示」バーを出す。読んでいる最中に表示がずれないよう、新着は自動では挿入しない
3. バーを押すと、新着を一覧に足して(重複する ID は除く。並び順は ID の新しい順なので、自分が先に投稿していれば、新着はその自分の投稿の下に入る)、基準の投稿 ID を足した新着の最大値まで進め、最上部へスクロールする
4. 新着が 50 件を超えるとき(hasMore)は「50件以上」と表示し、バーを押すと一覧を先頭から取り直す(手元の一覧との間に欠落ができるため)
5. 自分で投稿した投稿は、投稿時に先頭へ足すが、基準の投稿 ID は進めない。進めると、自分の投稿の直前に届いた他のユーザーの投稿が、以降の確認で見つからなくなる。確認の結果に含まれる自分の投稿(既に一覧にあるもの)は、新着として数えない

WebSocket / SSE によるサーバーからのプッシュは採用しません(将来の拡張候補)。

**投稿作成(F-05)**

1. 画面で文字数を検証する(画像機能の実装後は、画像があれば先に S3 へアップロードして imageKeys を得る。「画像投稿」参照)
2. POST /api/posts を呼ぶ
3. サーバーが再検証し、posts に保存する(画像機能の実装後は、post\_images も同じトランザクションで保存する)
4. 201 と作成した投稿を返す。画面は再読み込みなしで、一覧の先頭にその投稿を足し、入力欄を空にする

**投稿削除(F-06)**

1. カードの「削除」を押すと確認ダイアログを出す
2. DELETE /api/posts/{id} を呼ぶ
3. サーバーが「ログイン中のユーザーの投稿か」を確認し、投稿の行を物理削除する(コメント・いいね・画像は、実装後に ON DELETE CASCADE で一緒に消える)
4. 画面は一覧からそのカードを消し、「投稿を削除しました」とトーストを出す(投稿詳画面で削除したときは S-03 へ)

**投稿編集(F-23)**

1. 自分の投稿にだけ「編集」を出し、押すと、その場で本文を入力欄に切り替える(画像機能の実装後は、画像はそのまま表示し、変更できない)
2. 画面で 280 文字を検証し(残り文字数も表示)、「保存」で PUT /api/posts/{id} を呼ぶ
3. サーバーが「ログイン中のユーザーの投稿か」と本文を再検証し、本文を更新して updated\_at に現在時刻を入れる
4. 200 と更新後の投稿を返す。画面はカードの本文を置き換え、「編集済み」を表示する
5. 本文が変わっていないときは、更新せず(updated\_at も変えず)に 200 を返す

編集の履歴は保存しません。いいね・コメント・画像は編集してもそのまま残ります。タイムラインの並び順は投稿日時(created\_at)で、編集しても順番は変わりません。

## 3. API

一覧系の API は共通で、cursor(続きの位置)と limit(既定 20、最大 50)を受け、「{ items, nextCursor }」を返します。**投稿・タイムラインの API は、現在の実装ではすべてログイン必須です**(Authorization: Bearer)。エラーは共通の { code, message, fieldErrors? } 形式で、検証エラーは 400 VALIDATION_ERROR、他人の投稿は 403 FORBIDDEN、存在しない投稿は 404 NOT\_FOUND です。

| メソッド | パス | 認証 | リクエスト | 成功 | 失敗 |
| --- | --- | --- | --- | --- | --- |
| GET | /api/timeline | 必要 | tab(following を既定とする / all)、cursor, limit | 200 + { items: PostDto\[\], nextCursor } | 400 tab・cursor が不正 / 401 未ログイン |
| GET | /api/timeline/new | 必要 | tab, sinceId(一覧の先頭の投稿 ID) | 200 + { count, hasMore, items: PostDto\[\] }(sinceId より新しい投稿を新しい順に最大 50 件。超える場合は hasMore が true) | 400 tab が不正 / 401 |
| POST | /api/posts | 必要 | body(画像機能の実装後は imageKeys(0〜4) も) | 201 + PostDto | 400 検証エラー / 401 |
| GET | /api/posts/{id} | 必要 | なし | 200 + PostDto | 401 / 404 |
| DELETE | /api/posts/{id} | 必要 | なし | 204 | 401 / 403 他人の投稿 / 404 |
| GET | /api/users/{handle} | 必要(仮) | なし | 200 + UserProfileDto(「プロフィール」の機能定義書) | 401 / 404 |
| GET | /api/users/{handle}/posts | 必要(仮) | cursor, limit | 200 + { items: PostDto\[\], nextCursor } | 401 / 404 |
| PUT | /api/posts/{id} | 必要 | body | 200 + PostDto | 400 検証エラー(空・空白のみ・281 文字以上) / 401 / 403 他人の投稿 / 404 |

cursor は、直前のページ末尾の (created\_at, id) を Base64(URL セーフ)にした不透明な文字列です。不正な cursor は 400 になります。

**PostDto(投稿 1 件の形)**

現在の実装は次のフィールドです。

| フィールド | 型 | 説明 |
| --- | --- | --- |
| id | number | 投稿 ID |
| body | string | 本文 |
| createdAt | string(ISO 8601) | 投稿日時 |
| editedAt | string(ISO 8601) / null | 本文を編集した日時。null なら未編集。画面は null でないときに「編集済み」を出す |
| author | { id, handle, displayName, avatarKey? } | 投稿者 |
| likeCount | number | いいね数 |
| likedByMe | boolean | 自分がいいね済みか |
| commentCount | number | コメント数 |

次のフィールドは、画像機能の実装時に追加します。

| フィールド | 型 | 説明 |
| --- | --- | --- |
| images | { url, sortOrder }\[\] | 署名付き URL に変換済み(「画像投稿」参照) |

インプレッション数やリツイート数のフィールドは、PostDto に持たせません。

## 4. DB

一覧は、OFFSET ではなく「最後に見た投稿の (created\_at, id) より前」で続きを取ります(カーソル方式)。新しい投稿が途中で増えても、同じ投稿が二度出たり押し出されたりしません。cursor は (created\_at, id) を Base64 にした不透明な文字列として返します。

```sql
CREATE INDEX idx_posts_created ON posts (created_at DESC, id DESC);
CREATE INDEX idx_posts_user_created ON posts (user_id, created_at DESC, id DESC);

-- 一覧(フォロー中は、自分とフォロー中のユーザーの投稿)
SELECT p.*
FROM posts p
WHERE (p.created_at, p.id) < (:cursorCreatedAt, :cursorId)
  AND ( :tab = 'all'
        OR p.user_id = :me
        OR p.user_id IN (SELECT followee_id FROM follows WHERE follower_id = :me) )
ORDER BY p.created_at DESC, p.id DESC
LIMIT 21;
```

LIMIT は表示件数 + 1 を取ります。余る 1 件があれば続きがあると判断して nextCursor を返し、無ければ null を返します(先頭ページではカーソル条件を外します)。

**新着の確認**

新着は、時刻ではなく id で判定します(id は単調に増えるため、created\_at の同時刻や時計ずれの影響を受けません)。50 件を超えて取れるかを見るため、51 件を取って切り捨てます。

```sql
SELECT p.*
FROM posts p
WHERE p.id > :sinceId
  AND ( :tab = 'all' OR p.user_id = :me )
ORDER BY p.id DESC
LIMIT 51;
```

**N+1 問題を避ける**

- 投稿の 20 件を取った後に、投稿者・画像・いいね数・コメント数・いいね済みを、投稿 ID の一括(IN)でまとめて取る
- いいね数・コメント数は GROUP BY post\_id で、1回のクエリで 20 件分を数える
- 投稿 1 件ごとにクエリを発行しない

**削除時の連動**

posts を削除すると、外部キーの ON DELETE CASCADE で comments・likes・post\_images の行も消えます。S3 の画像ファイルを消すための流れは、「画像投稿」の機能定義書に書きます。

**編集時の更新**

posts に updated\_at(NULL 可)を持ちます。編集したときだけ現在時刻を入れ、作成時は NULL のままにします。

```sql
ALTER TABLE posts ADD COLUMN updated_at TIMESTAMPTZ;

UPDATE posts
SET body = :body, updated_at = now()
WHERE id = :id AND user_id = :me;  -- 0 件なら他人の投稿または無い投稿
```

自分の投稿かどうかの確認を WHERE 句に含めることで、確認と更新の間に割り込まれても他人の投稿を書き換えないようにします。サービスは先に投稿を取得して 404(無い)/ 403(他人の投稿)を判定し、その後の更新で 0 件だったとき(確認の後に削除された場合)は 404 を返します。削除(DELETE)も同じ WHERE 句で行います。

## 5. エラーと境界値

- 本文がちょうど 280 文字は可、1 文字超えは 400。絵文字・日本語は 1 文字と数える(Java では length() ではなく codePointCount を使う)
- 同じ投稿の二重送信: 送信中はボタンを無効化する。サーバー側での重複判定はしない(同じ文面の連投は許す)
- 存在しない投稿やすでに削除された投稿を開いたとき: 404 を返し、「投稿が見つかりません」と表示する
- 他人の投稿を DELETE したとき: 403。画面でボタンを出さないだけではなく、サーバーで必ず拒否する
- どのタブでも 0 件のとき: 空状態の文言を表示する
- 編集で本文を空にしたとき: 400(現在は画像が無いため常に不可。画像機能の実装後は、画像がある投稿は可、画像が無い投稿は 400「本文または画像を入れてください」)
- 新着の確認が通信エラーになったとき: 何も表示せず、次回(30 秒後、または画面が見える状態に戻ったとき)に再確認する
- 他のタブへ切り替えた直後に前のタブの応答が返ったとき: 応答を捨て、前のタブの一覧を表示しない
- 他人の投稿を PUT したとき: 403。編集中に投稿が削除されたときは 404 となり、「投稿が見つかりません」と表示して一覧から消す
- 編集中に「キャンセル」を押したとき: 入力を捨てて元の本文に戻す(確認は出さない)

- [x] 「全体」タブには、フォローしていない人の投稿も出る
- [x] 280 文字で投稿でき、281 文字では画面とサーバーの両方で拒否される
- [ ] 画像だけの投稿と、文章だけの投稿ができる(文章だけは可。画像は未実装)
- [ ] 各カードにいいね数とコメント数が出ていて、インプレッション数はどこにも出ていない(いいね・コメントの実装後に確認。インプレッション数は出していない)
